# v0.3 integration contract

Rust owns all app state, timing, progress, presence and dialogue. Frontend schema is src/app-state.ts; use serde camelCase. Stage 1/2/3. Pet windows render snapshots, never award growth. State event: app-state. Commands: get_app_state() -> AppSnapshot; dispatch_action(action: AppAction, expectedRevision?: number) -> AppSnapshot; open_settings(); request_input_access(). Revision optional only for explicit non-stale-independent integration, UI send last snapshot revision. Errors on stale revision refresh state, never blind-retry mutations.

Actions: close(pet), summon(pet), activity(pet,activity), join(pet=dragged,ownLeft), split, pomodoro-start/pause/resume/stop, settings(settings), skip-sleep. Join chooses stationary activity, refuses double sleep before stage 3. Pair owner=dragged. Preserve pre-pair states with schedule generation. Close can dissolve pair with either remaining member. Last close backend reports none present; runtime saves/exits. Core plain code cannot call Tauri.

Input module API: InputCounter::start() -> Self, set_enabled(bool), drain() -> InputBatch { keys:u64, clicks:u64, available:bool, locked:bool }, request_access(), status() -> String, shutdown(). Methods use &self; Send+Sync for managed state. Platform callback counters must be read/reset atomically; no per-event IPC. Lock state supported. Core tick takes explicit unix seconds/local date/minute and input deltas; runtime owns chrono/time acquisition.

Runtime integration: one `Runtime` managed by Tauri, one `pet-state-clock` thread, one `InputCounter`. `with_batch(f)` holds the input lock across draining and the pure core transition. All runtime paths use the fixed lock order **Session/Core → input**; never call an input method from the closure. Close/summon use tick(old presence) → dispatch(new presence) in that closure, then save outside the input lock. Rejected commands still retain input already settled. `elapsed_seconds` comes from `Instant`; local calendar comes from `chrono::Local`. Statistical ticks accept pending UI revisions, but semantic transitions and previous commands invalidate them. Frontends never auto-retry a stale mutation.

Real-time count stream (2026-09-14 audit): the same clock pulses every 32ms. On input or gate changes it settles one batch immediately; without input, passive time advances every second. Full `app-state` broadcasts occur once a second or on semantic transitions, while lightweight `input-counts` broadcasts contain only sequence, stateRevision, inputStatus and each pet's day/todayKeys/todayClicks. Counts are authoritative core totals, not speculative sums; no second consumer drains native input. `get_input_counts` provides initial stream state; `get_input_health` returns only permission/listener/lock booleans and a status token. Frontends reject out-of-order counter sequences and never replace newer live totals with older full snapshots. Disk writes remain on the existing save cadence, not per event/pulse.

The independent desktop counter panel (`counter.html`) and settings page both reuse this stream. `open_counter()` creates or shows one non-initially-focused, always-on-top resizable window; it does not create a collector, clock or write to personal progress. Settings, pet context menus and the Mac menu bar expose the entry. Hiding the panel does not stop collection. Only explicit user entry opens it; background updates never call focus/show. Browser-only `?preview=1` is clearly labelled simulated and never activates inside Tauri. A settings UI refresh may read health but must not request OS permission; only its explicit permission action may do that.

Daily growth sources: `Progress.dailySources={companion,keyboard,mouse}` contains actual credited rewards after caps. `dailyFocusEarned` is the existing focus source. Companion includes awake and pet-sleep base awards. Keyboard/mouse share a cap-truncated batch proportionally without changing the original combined reward. The residual `dailyEarned - dailyFocusEarned - sum(dailySources)` is unclassified historical credit, never reconstructed from counts. Optional/default-zero fields keep version-3 saves readable; forward day rollover resets all daily sources and totals, while clock reversal does not. New writes validate finite nonnegative source values and their sum against the daily total (with floating-point tolerance).

Input starts disabled until the saved `inputEnabled` preference is applied (default true). Existing OS permission is sufficient; there is no extra per-launch consent gate. Only an explicit settings action requests missing macOS Input Monitoring permission.

Save failure leaves ordinary actions in memory with a storage warning, preserving their input ownership boundary. If closing the final pet cannot save, closing is cancelled and the previous presence is restored at another atomic input boundary. Native window visibility follows versioned snapshots and is separate from presence; no native UI call is made while holding the core/input locks.

Settings UI is independent settings.html + src/settings.ts/css; imports app-state.ts and dialogue-catalog.ts if present. Main agent handles Cargo, npm, vite, capabilities, existing files lib.rs/window-pet.ts/main.ts/macos.rs/assets.ts. Agents own separate new files only. No native window mock tests, no UI automation, no long runs. Only pure tests and compilation. Art is candidate awaiting user approval.
